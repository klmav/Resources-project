# Тест-кейсы: Resource Plan Auditor Bot

Нотация:
- **Команда**: что запускаем (`audit-xlsx`, Telegram `/audit`, `/summary`)
- **Входные данные**: XLSX/контекст
- **Ожидаемо**: ключевые `Issue.code`/поведение

---

## A. Парсинг XLSX

### A1. Авто-выбор файла (path=auto)
- **Команда**: `python -m src.main audit-xlsx --path auto`
- **Входные данные**: в папке проекта есть хотя бы один `.xlsx`
- **Ожидаемо**: выбирается первый `.xlsx`, команда не падает

### A2. Не найден XLSX
- **Команда**: `python -m src.main audit-xlsx --path auto`
- **Входные данные**: в папке нет `.xlsx`
- **Ожидаемо**: понятная ошибка `FileNotFoundError`

### A3. Определение шапки
- **Команда**: `audit-xlsx`
- **Входные данные**: строка с `A/D` в колонке A и датами месяцев в строке
- **Ожидаемо**: `HeaderHasMonthsCheck` не ругается

---

## B. Проверки данных (2026)

### B1. Пустые месяцы = ошибка (агрегация по строке)
- **Команда**: `audit-xlsx`
- **Входные данные**: строка сотрудника (J) с пустыми ячейками в текущем месяце и следующем (план на 2 месяца вперед)
- **Ожидаемо**: 1 issue `MONTH_CELL_EMPTY` на строку, с перечислением месяцев (MM.YY), severity red

Дополнение (важное):
- если в строке есть план **в любом другом месяце 2026** (например план начинается с марта),
  то текущий+следующий месяц всё равно должны быть **не пустыми** (обычно 0).

### B2. Шаг 0.5 (валидно)
- **Команда**: `audit-xlsx`
- **Входные данные**: значения `0`, `0.5`, `1`, `1.5`, `10.5`
- **Ожидаемо**: нет `MONTH_CELL_NOT_HALF_STEP`

### B3. Шаг 0.5 (невалидно)
- **Команда**: `audit-xlsx`
- **Входные данные**: `9.66`, `13.73`
- **Ожидаемо**: `MONTH_CELL_NOT_HALF_STEP` severity red

### B4. Не число в ячейке месяца
- **Команда**: `audit-xlsx`
- **Входные данные**: `#REF!`, `N/A`, `abc`
- **Ожидаемо**: `MONTH_CELLS_NUMERIC` severity red

### B5. Отрицательное значение
- **Команда**: `audit-xlsx`
- **Входные данные**: `-1`
- **Ожидаемо**: `MONTH_CELLS_NONNEGATIVE` severity red

### B6. Превышение рабочих дней месяца
- **Команда**: `audit-xlsx`
- **Входные данные**:
  - строка 1 (workdays) для месяца = 19
  - строка сотрудника в этом месяце = 20
- **Ожидаемо**: `ALLOCATION_EXCEEDS_WORKDAYS` severity red

### B7. in? = False, но есть дни
- **Команда**: `audit-xlsx`
- **Входные данные**: `in?` = False и любой месяц 2026 > 0
- **Ожидаемо**: `IN_FLAG_INCONSISTENT` severity yellow + корректная привязка `pm/person`

### B8. Не заполнены обязательные поля A/B/C/D/F/G/H/I/J при наличии дней
- **Команда**: `audit-xlsx`
- **Входные данные**: месяц 2026 > 0 и пустые поля из списка
- **Ожидаемо**: `KEY_FIELDS_FILLED` severity yellow (на каждое поле)

### B9. Пустой PM при наличии дней (>0)
- **Команда**: `audit-xlsx`
- **Входные данные**: в строке есть любой месяц 2026 > 0, а колонка I (PM) пустая
- **Ожидаемо**: `PM_MISSING` severity red

### B10. Пустое ФИО сотрудника (J) при наличии дней (>0)
- **Команда**: `audit-xlsx`
- **Входные данные**: в строке есть любой месяц 2026 > 0, а колонка J пустая
- **Ожидаемо**: `EMPLOYEE_MISSING` severity red

### B11. Сумма по сотруднику в месяце НЕ превышает рабочие дни (горизонт 2 месяца)
- **Команда**: `audit-xlsx`
- **Входные данные**:
  - для сотрудника J есть несколько строк задач
  - сумма по всем строкам в текущем месяце и следующем не должна превышать рабочие дни (строка 1)
- **Ожидаемо**: при превышении `EMPLOYEE_MONTH_SUM_EXCEEDS_WORKDAYS` severity red

### B12. Роль в колонке A
- **Команда**: `audit-xlsx`
- **Входные данные**:
  - валидные: `A`, `D`, `PM`, `BI`
  - невалидные: `X`, `DEV`
- **Ожидаемо**:
  - для валидных — нет ошибки
  - для невалидных — `ROLE_CODE_INVALID` severity red

### B13. Проверяем только 2026 (активный год из M2)
- **Команда**: `audit-xlsx`
- **Входные данные**: наличие колонок месяцев 2025 и 2026, M2=2026
- **Ожидаемо**: ошибки формируются только по месяцам 2026

## C. Формирование отчета (CLI)

### C1. Сводка и топ по PM
- **Команда**: `audit-xlsx --limit 50`
- **Ожидаемо**:
  - есть “Топ проблем по типу”
  - есть “Пустые месяцы по PM” (если есть `MONTH_CELL_EMPTY`)
  - вывод не бесконечный, присутствует “… и ещё N” при превышении limit

### C2. Полный вывод
- **Команда**: `audit-xlsx --full`
- **Ожидаемо**: печатаются все issues (может быть очень длинно)

## D. Telegram (без GPT)

### D1. /audit (без аргументов) показывает кнопки PM
- **Команда**: `/audit`
- **Ожидаемо**: сообщение с inline-клавиатурой и кнопкой “Все PM”

### D2. /audit <PM> фильтрует
- **Команда**: `/audit Яковлева Елена`
- **Ожидаемо**: отчет только по issues этого PM

### D3. Кнопка PM запускает аудит
- **Команда**: нажать кнопку PM в ответ на `/audit`
- **Ожидаемо**: приходит отчет для выбранного PM

### D4. Длинные сообщения режутся на чанки
- **Команда**: `/audit` на большом файле
- **Ожидаемо**: бот присылает несколько сообщений, без ошибок Telegram

---

## F. Исправления (preview/apply) для XLSX

### F1. /fix preview (без аргументов)
- **Команда**: `/fix preview`
- **Ожидаемо**: бот сообщает, сколько ячеек будет заполнено `0` (пустые на 2 месяца вперед)

### F2. /fix preview <PM>
- **Команда**: `/fix preview Яковлева Елена`
- **Ожидаемо**: preview только для выбранного PM

### F3. /fix apply без preview
- **Команда**: `/fix apply`
- **Ожидаемо**: бот просит сначала сделать preview

### F4. /fix apply после preview
- **Команда**: `/fix preview` → `/fix apply`
- **Ожидаемо**: создается копия XLSX (в `out/`), применяется нужное количество правок

### F5. Preview показывает примеры (top‑10)
- **Команда**: `/fix preview`
- **Ожидаемо**: в сообщении есть список примеров с адресом ячейки и месяцем (например `Z5, 01.26`)

### F6. Подсветка PM/сотрудника
- **Команда**: `/fix preview` → `/fix apply`
- **Входные данные**: в строке есть дни > 0, но PM (I) или сотрудник (J) пустые
- **Ожидаемо**: в копии XLSX соответствующие ячейки подсвечены (без автозаполнения значений)

### F7. Подсветка некорректных значений месяцев
- **Команда**: `/fix preview` → `/fix apply`
- **Входные данные**:
  - в месячных ячейках есть не число / отрицательное / не кратно 0.5 / > рабочих дней
- **Ожидаемо**:
  - такие ячейки подсвечены в копии XLSX
  - в preview видно “подсветить некорректные значения месяцев: N ячеек” + примеры с причиной

### F8. Подсветка ошибок в строке рабочих дней (сервисная строка)
- **Команда**: `/fix preview` → `/fix apply`
- **Входные данные**:
  - в строке рабочих дней (строка над шапкой) для какого‑то месяца стоит `#REF!` / текст / `0` / отрицательное число
- **Ожидаемо**:
  - в preview видно “подсветить сервисную строку (рабочие дни): N ячеек” + примеры
  - в копии XLSX подсвечены проблемные ячейки в сервисной строке
  - в примерах/причине есть `WORKDAYS_ROW_NUMERIC`

### F9. Подсветка некорректных ролей / in? / пустых ключевых полей строки
- **Команда**: `/fix preview` → `/fix apply`
- **Входные данные**:
  - колонка A: роль не из `A/D/PM/BI` (например `X`)
  - в строке есть дни > 0 в каком‑то месяце
  - `in? = False`, но при этом есть дни
  - одно из ключевых полей (A/B/C/D/F/G/H) пустое при наличии дней
- **Ожидаемо**:
  - в preview видны счетчики:
    - “подсветить некорректные роли: N”
    - “подсветить 'in?' (есть дни, но False): N”
    - “подсветить пустые ключевые поля строки: N”
  - в копии XLSX подсвечены:
    - роль (колонка A) с причиной `ROLE_CODE_INVALID`
    - `in?` (колонка K) с причиной `IN_FLAG_INCONSISTENT`
    - пустые ключевые поля с причиной `KEY_FIELDS_FILLED`

## E. Telegram + GPT‑5

### E1. /summary без OPENAI_API_KEY
- **Команда**: `/summary`
- **Ожидаемо**: понятное сообщение “не задан OPENAI_API_KEY”

### E2. /summary (без аргументов) показывает кнопки PM
- **Команда**: `/summary`
- **Ожидаемо**: inline-клавиатура выбора PM

### E3. /summary <PM> фильтрует контекст
- **Команда**: `/summary Клименко Алексей`
- **Ожидаемо**: GPT‑5 получает context с filter.pm, ответ касается только этого PM

### E4. Формат ответа GPT‑5
- **Команда**: `/summary` (при включенном ключе)
- **Ожидаемо**: ответ содержит секции:
  - “Приоритеты”
  - “Что сделать”
  - “По PM”
  - “Уточнения” (опционально)

## F. Чат‑режим (свободный текст)

### F1. Сообщение без контекста
- **Команда**: отправить текст без запуска /audit (например: “что исправить?”)
- **Ожидаемо**: бот просит сначала запустить `/audit` или нажать кнопку PM

### F2. Сообщение с контекстом (после /audit)
- **Команда**:
  1) `/audit` → выбрать PM
  2) отправить: “что самое критичное?” / “что мне делать дальше?”
- **Ожидаемо**: GPT‑5 отвечает коротко (3–8 bullets) строго по результатам проверок

### F3. Вопрос “по PM” в свободном тексте
- **Команда**:
  1) `/audit` → выбрать PM
  2) отправить: “что исправить у PM <ФИО>?”
- **Ожидаемо**: бот отвечает по доступному контексту; если нужен другой PM — подсказывает `/audit <PM>` или кнопки

## G. Загрузка сотрудника (ч/д и %)

### G1. /load базовый
- **Команда**: `/load Иванов Иван 01.26`
- **Ожидаемо**: бот отвечает:
  - запланировано N ч/д
  - норма (рабочие дни) M
  - загрузка P%

### G2. /load если не найдены рабочие дни
- **Вход**: в сервисной строке над шапкой в месяце пусто/не число
- **Команда**: `/load Иванов Иван 01.26`
- **Ожидаемо**: бот пишет ч/д, но сообщает что процент посчитать нельзя

### G3. Свободный текст “загрузка”
- **Команда**: “Какая загрузка у Иванов Иван в 01.26?”
- **Ожидаемо**: ответ как в G1

---

## H. “Не исправлено N дней” (persistency)

### H1. История создается после первого запуска
- **Команда**: `/audit`
- **Ожидаемо**: создается файл истории `out/issue_history.json` (или по `ISSUE_HISTORY_PATH`)

### H2. В weekly‑отчёте появляется блок “держатся ≥ N дней”
- **Предусловие**: есть red‑проблема, которая сохраняется в нескольких запусках и старше `PERSISTENT_RED_DAYS`
- **Ожидаемо**: в еженедельном отчёте есть секция:
  - “Критичные проблемы держатся ≥ … дней”
  - список проблем с количеством дней

---

## I. Дельта недельного отчёта (новое/исправлено/ухудшилось/улучшилось)

### I1. Первый weekly‑отчёт
- **Предусловие**: нет `out/issue_snapshot.json`
- **Ожидаемо**: бот пишет, что это первый отчёт и дельту не считает, и сохраняет снапшот

### I2. Второй weekly‑отчёт
- **Предусловие**: есть прошлый снапшот
- **Ожидаемо**: в weekly‑сообщении есть блок Δ с числами:
  - новое / исправлено / ухудшилось / улучшилось
  - отдельные списки: “🔴 Новые критичные (top‑3)” и “✅ Исправленные критичные (top‑3)” (если такие есть)

## Примечание: тестовые файлы

Рекомендуется создать отдельные маленькие файлы (фикстуры) для автоматизированных тестов,
чтобы не зависеть от большого `AK Рес план.xlsx`.
