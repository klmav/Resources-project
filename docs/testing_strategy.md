# Стратегия тестирования: Resource Plan Auditor Bot

## Цели тестирования

- **Корректность проверок**: детерминированные правила должны находить ошибки и не давать ложных срабатываний на валидных данных.
- **Стабильность парсинга**: XLSX/Sheets должны корректно интерпретироваться при небольших изменениях (пустые строки, пробелы, формат чисел, даты).
- **Полезность отчетов**: вывод должен быть читаемым, не “спамить” и содержать приоритеты (топ по типам, топ по PM).
- **Надежность интеграций**:
  - Telegram: команды, фильтры, inline-кнопки, лимит длины сообщений
  - GPT‑5: корректный контекст, стабильный формат ответа, безопасные ограничения (не выдумывать данные)

---

## Уровни тестирования

### 1) Unit-тесты (точечные)

Фокус:
- функции парсинга и нормализации (`src/local/xlsx_reader.py`)
- математика правил (шаг 0.5, сравнение с рабочими днями)
- фильтрация issues по PM/Person
- расчёт загрузки `/load` (сумма ч/д и %)
- история проблем (“не исправлено N дней”)

Преимущества:
- быстрые, детерминированные
- легко воспроизводятся

### 2) Интеграционные тесты (локально)

Фокус:
- `audit-xlsx` end-to-end: чтение XLSX → проверки → отчет
- Telegram handlers: вызов команд → формирование текста → разбиение на чанки

Примечание: Telegram и OpenAI лучше тестировать через “моки”/заглушки, чтобы не зависеть от сети.

### 3) E2E (ручные)

Фокус:
- реальный Telegram бот:
  - `/audit`
  - `/audit <PM>`
  - `/person <ФИО>`
  - `/load <ФИО> <месяц>`
  - `/summary`
  - `/summary <PM>`
  - кнопки выбора PM
  - `/fix preview` → `/fix apply` (копия XLSX)
- еженедельное уведомление (среда) + блок “не исправлено N дней”
- реальный GPT‑5 ответ (по ключу), с проверкой, что формат соблюден

---

## Среды тестирования

- **dev/local**: тестируем на локальной выгрузке XLSX (`AK Рес план.xlsx`)
- **staging** (опционально): отдельный бот/ключи, тестовая копия XLSX/Sheets
- **prod**: только после стабилизации, с мониторингом

---

## Подходы и техники

### Тест-данные

Рекомендуется держать набор минимальных XLSX/CSV фикстур:
- “валидный минимум”
- “пустые месяцы”
- “дроби не кратны 0.5”
- “in?=False при наличии дней”
- “перегруз (дни > рабочих дней)”

Фикстуры должны быть без персональных данных (анонимизация).

### Оракулы (ожидаемые результаты)

Каждый тест должен четко проверять:
- код проблемы (`Issue.code`)
- severity
- ключевую часть сообщения
- привязку (PM, person, month)

### Нестабильные части (LLM)

GPT‑5 тестируем иначе:
- не сравниваем полный текст 1-в-1
- проверяем “контракт ответа”:
  - наличие секций: Приоритеты / Что сделать / По PM / Уточнения (опционально)
  - отсутствие выдуманных чисел/фактов (проверка по ключевым значениям из контекста)
  - длина/читабельность

---

## Критерии приемки (Definition of Done)

- `audit-xlsx` на контрольных файлах дает ожидаемые `Issue.code` и не падает
- Telegram:
  - команды не падают
  - длинные ответы корректно делятся на чанки
  - кнопки PM работают и не ломаются при большом количестве PM
- “не исправлено N дней”:
  - история обновляется между запусками
  - в еженедельном отчёте появляется блок про red‑проблемы, которые держатся ≥ N дней
- GPT‑5:
  - при отсутствии ключа дает понятную ошибку
  - при наличии ключа возвращает ответ в заданном формате

---

## Регрессия (что проверяем перед релизом)

- 5–10 контрольных кейсов на XLSX
- 5 ручных сценариев в Telegram
- 1 сценарий `/summary <PM>` с GPT‑5 (если включено)
